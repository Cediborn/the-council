# COUNCIL V0.3 — Conversational Intelligence & Interaction Upgrade — SPEC

Status: **Approved design (pre-implementation).**
Scope: **Intelligence + conversational interaction only. NO UI redesign. NO premium characters. NO Challenge full-build.**
Follows: V0.2.2.4 (performance forensics) which left the pipeline at DEEP ≈ 670–1050s on the local CPU model.

---

## 1. Product principle

> The Council must NOT assume the user knows how to prompt an AI.
> The Council's job is **"help the user make a better decision"**, not "judge whether the prompt was good".

A technically perfect answer to a poorly written prompt is a poor product experience. This version makes the Council work with humans as they actually are: informal, incomplete, ambiguous, and conversational.

## 2. Current-state audit (verified against code, not docs)

| Concern | Current reality |
|---|---|
| Pipeline | `POST /api/council` → `runCouncil` (orchestrator) → SSE events (`convened` → `agent:start/done` → `comparison` → `da:done` → `reassessment:done` → `verdict` / `error`). QUICK = 3 agents + Judge; FULL = 4 agents + comparison + Judge; DEEP = + Devil's Advocate + Reassessment. |
| Interaction | **Single-shot.** After a verdict the only actions are `reset()` (new question), `retryAgent()` (failed member), or reopen a stored session. **There is no follow-up, no clarification, no conversation loop anywhere** (confirmed by search: zero `followUp|conversation|thread|turn|clarif` hits in app logic). |
| Classification | `classifyQuestion` — deterministic keyword heuristic → type + ordered capabilities. Known false-positive bug: `script` ⊂ `subscription` classifies a subscription-box question as `technical`. No ambiguity detection, no missing-info signal. |
| Judge | Zod-validated; never vote-counts; per-type verdict sets; reports `informationSufficiency` (HIGH/MEDIUM/LOW), `criticalUnknowns`, `whatWouldChangeVerdict`, `whyThisVerdictWon`. `INSUFFICIENT_INFORMATION` is system-reserved (only the deterministic synthesizer can emit it). **Sufficiency is already separate from the verdict — the gap is conversational, not structural.** |
| Client state | `councilReducer` — phases idle/analyzing/partial_results/council_complete/judging/complete/degraded/failed/cancelled; events deduped; sessions persisted to localStorage (`council.sessions.v1`, max 10, 500KB cap). No "turn" concept. |
| UI components | `QuestionScreen`, `DeliberationPanel`, `VerdictView`, `ExpandableAnalysis`, `ChallengeButton` (future placeholder), `InsufficientPanel`, `CouncilApp` (wires `run/reset/cancel/retryAgent`). |
| Cost reality | Local model ~5 tok/s generation, ~550 tok/s eval. FULL ≈ 8 min, DEEP ≈ 11–17 min. **Every follow-up decision is a cost decision.** |

## 3. Interview decisions (user-confirmed, 4 rounds)

| # | Decision | Choice |
|---|---|---|
| 1 | Conversation presentation | **Threaded turns + revision diff.** Every verdict stays in the thread; each re-deliberation shows the NEW verdict plus a compact "what changed vs previous" summary. |
| 2 | Missing critical context | **Ask first, then convene.** Up to 2 targeted questions; the Council waits for answers, then deliberates with that context. |
| 3 | Follow-up types | **Two paths.** Intent classifier splits replies: new-info/corrections → (targeted) re-deliberation; explanation requests → direct answer WITHOUT re-convening. |
| 4 | Re-deliberation weight | **Targeted re-analysis.** Re-run only the agents whose lens the new info touches; reuse untouched analyses; then comparison + Judge. |
| 5 | Question Understanding layer | **Hybrid.** Heuristics gate; the LLM "understander" runs only when the gate flags ambiguity/incompleteness (or always when a cloud provider is available). |
| 6 | Clarification question generation | **Bank first, LLM fallback.** Deterministic question bank for common gaps (budget/time/market/location/scale/competition); LLM only for unusual cases. Hard cap: 2 questions. |
| 7 | Verdict sets | **Refine per question type** (see §9). Product-flavored sets stay for business-flavored types; new natural sets for math/explanation/argument/technical/troubleshooting. |
| 8 | Follow-up mode | **Auto-degrade to lighter.** Re-deliberation always runs the lighter pipeline (targeted agents + Judge, no Devil's Advocate / Reassessment) regardless of the original mode. |
| 9 | Re-deliberation trigger | **Always explicit.** No auto-trigger from matching `whatWouldChangeVerdict` conditions; the intent classifier alone decides (with the previous verdict's change-conditions available as context to the classifier). |
| 10 | Thread persistence | **Summarized turns.** Store question + reply + final verdict + diff per turn (no raw per-turn analyses). Existing single-session store untouched. New storage key. |
| 11 | Turn limit | **Soft limit.** After ~6–8 turns the Council notes the thread is long and suggests a fresh session; user may continue. |
| 12 | Casual input | **Quick chat reply.** Small-talk/acknowledgments get a brief natural reply (no Council run, no re-deliberation), thread intact. |
| 13 | Clarification skip path | **Answer or abandon.** When a clarification round is asked, the Council waits for answers; abandoning cancels that deliberation. *(Mitigation: the round only triggers when the hybrid gate flags decision-critical gaps, so casual users rarely hit it.)* |

## 4. New architecture overview

```
USER INPUT
   │
   ▼
[1] INTENT GATE (deterministic, free)
   │  small-talk → QUICK CHAT REPLY (no Council)
   │  follow-up reply → [5]
   │  new question → [2]
   ▼
[2] CLASSIFY + UNDERSTAND (hybrid)
   │  classifyQuestion (existing)
   │  heuristic gap-detector → decision-critical gaps?
   │     ├─ no  → CONVENE (with explicit assumptions)
   │     └─ yes → LLM UNDERSTANDER (only then)
   │              → restated intent + inferred assumptions
   │              → [3] CLARIFICATION ROUND (bank-first, max 2 Qs)
   ▼
[3] CLARIFICATION ROUND          (answer or abandon)
   │  user answers → context merged → CONVENE
   ▼
[4] COUNCIL DELIBERATION (existing pipeline, unchanged)
   ▼
   VERDICT  ──▶ thread turn with diff vs previous
   ▼
[5] FOLLOW-UP INTENT CLASSIFIER (deterministic + optional LLM)
   ├─ SMALL_TALK            → quick chat reply
   ├─ EXPLANATION_REQUEST   → DIRECT ANSWER (single small call, no Council)
   ├─ CORRECTION            → context update → TARGETED RE-ANALYSIS (lighter)
   ├─ NEW_INFORMATION       → context update → TARGETED RE-ANALYSIS (lighter)
   ├─ CHALLENGE             → explicit challenge intent (existing ChallengeButton future-mode; v0.3 wires intent only)
   └─ NEW_QUESTION          → start a new conversation thread
```

**Non-negotiable rules carried from V0.2.2.x:**
- No fake progress. Every UI state maps to a real event.
- Agent/Judge failures degrade gracefully; completed analyses are never gated behind the Judge; no fabrication.
- No majority-vote fallback anywhere; `INSUFFICIENT_INFORMATION` remains system-reserved.
- Stateless server (safe on serverless): conversation context travels with each request.
- Never expose secrets; model output always Zod-validated before rendering.

## 5. Data model — conversation thread

New types (in `lib/council/types.ts` or a new `lib/council/conversation.ts`):

```ts
type FollowUpIntent =
  | "SMALL_TALK"          // quick chat reply
  | "EXPLANATION_REQUEST" // direct answer
  | "CORRECTION"          // re-deliberate (targeted)
  | "NEW_INFORMATION"     // re-deliberate (targeted)
  | "CHALLENGE"           // explicit challenge
  | "NEW_QUESTION";       // fresh thread

interface ConversationTurn {
  id: string;
  kind: "user" | "assistant";
  type:
    | "question"          // original question
    | "clarification"     // Council asked, user answered
    | "verdict"           // a verdict card (with diff vs previous)
    | "direct_reply"      // explanation answer
    | "chat_reply"        // small-talk reply
    | "revision";         // re-deliberated verdict
  payload: {
    text?: string;
    answers?: { question: string; answer: string }[];
    verdict?: CouncilVerdict;
    usage?: CouncilUsage;
    diff?: VerdictDiff;   // only on verdict/revision turns (null on first)
    intent?: FollowUpIntent;
  };
  startedAt: number;
}

interface VerdictDiff {
  changed: boolean;
  verdictChanged: boolean;        // category differs
  scoreDelta: number;             // new - old
  confidenceDelta: number;
  reasonsAdded: string[];
  reasonsRemoved: string[];
  summaryNote: string;            // 1-2 sentence "what changed"
}

interface ConversationThread {
  id: string;                     // stable conversation id
  mode: CouncilMode;              // original mode (revisions auto-degrade)
  turns: ConversationTurn[];
  latestVerdict?: CouncilVerdict;
  latestUsage?: CouncilUsage;
  context: {
    originalQuestion: string;
    classification: QuestionClassification;
    mergedContext: string[];      // accumulated corrections/new info
    explicitAssumptions: string[];
    answeredClarifications: { q: string; a: string }[];
  };
}
```

**Turn limit:** at turn ~6–8 the assistant attaches a soft note suggesting a fresh thread; user may continue.

## 6. Question Understanding layer (`lib/council/understand.ts` + `lib/council/understander.ts`)

### 6.1 Deterministic intent gate (`intentGate(text, thread?)`)
- Small-talk regex/word sets: `hi|hello|hey|thanks|thank you|ok|okay|cool|nice|lol|haha|great` (+ variants, contraction-aware). → `SMALL_TALK`.
- If a thread exists → route to follow-up classifier (§8). Otherwise new question.

### 6.2 Heuristic gap detector (`detectGaps(question, classification)`)
Runs on every new question (free, deterministic). Returns a list of *decision-critical* missing items, using type-aware rules:

| Gap key | Trigger (examples) | Question types where critical |
|---|---|---|
| `budget` | no money/cost figure for purchase/start/plan | decision, business, planning, comparison |
| `timeline` | no when/deadline for plan/decision | planning, decision, business |
| `market` | business idea without audience/competition mention | business |
| `location` | move/study/relocate without target country/city | decision, educational, planning |
| `scale` | "app"/"business"/"project" without size/scope | business, technical, creative |
| `goal` | "should I do X" without the outcome wanted | decision, general |
| `context` | pronouns/elliptical "this"/"it" without antecedent | all |

**Output:** `{ gaps: Gap[]; critical: boolean }` — `critical=true` only if ≥1 gap is in the type's critical set. The gate exists so the LLM understander (and thus the clarification round) only fires when it materially matters.

### 6.3 LLM understander (`understandQuestion`) — only when gate is critical, or cloud provider available
One small model call (`stage: "understanding"`, tight cap ~400 tokens). Zod schema:

```ts
const understanderSchema = z.object({
  restatedQuestion: z.string().min(1).max(800),
  intent: z.string().min(1).max(300),            // what the user actually wants
  inferredAssumptions: z.array(z.string().max(200)).max(4).default([]),
  missingCritical: z.array(z.string().max(200)).max(3).default([]),
  reframing: z.string().max(300).default(""),    // optional better framing
});
```

If the call fails/times out/malformed → **graceful fallback**: proceed to convene with the heuristic gaps as explicit assumptions + missing-info list (never block on the understander). If it succeeds and `missingCritical` is non-empty → clarification round (§7).

### 6.4 Assumptions made explicit
Every convened run embeds in the agent context + verdict context:
- `explicitAssumptions` (from understander or heuristic inference), formatted like *"Assumption: I'm treating your question as … — correct me if that's wrong."*
- Unanswered clarification questions become `criticalUnknowns` / `whatWouldChangeVerdict` items on the verdict.

## 7. Clarification round (`lib/council/clarification.ts`)

- **Question bank (primary):** keyed by gap key → templated, plain-language questions with a "why it matters" line. Examples:
  - budget → *"What's your rough budget for this? It changes the recommendation a lot — e.g. 'under $500' vs '$5,000+'."*
  - timeline → *"When do you need this sorted? A 2-week plan looks very different from a 2-year one."*
  - market → *"Who are the customers, and what do you know about the competition so far?"*
  - location → *"Which city/country are you thinking of?"*
  - scale → *"How big are you imagining this — a small test, or a full build?"*
- **LLM fallback:** when no bank question fits the detected gap (unusual case), the understander proposes ≤2 questions under a strict schema `{ questions: [{ question, whyItMatters }] }` with `.max(2)`.
- **Hard cap: 2 questions** shown at once. No ten-question dumps.
- **Answer or abandon (user decision #13):** the round waits; abandoning cancels the deliberation (the thread keeps the turns; user can re-ask). Answers merge into `context.mergedContext` and are re-fed to the agents via the user prompt.
- New request path: `POST /api/council/clarify` → `{ question, mode, gaps }` → `{ questions?, restatedQuestion?, assumptions? }`. Client shows them; answers return with the convene request as `context.clarifications`.

## 8. Follow-up intent classifier + two execution paths (`lib/council/followup.ts`)

### 8.1 Classifier
Deterministic signals first, LLM only for ambiguous cases:

| Intent | Deterministic signal | Fallback LLM |
|---|---|---|
| `SMALL_TALK` | greeting/ack regex | — |
| `EXPLANATION_REQUEST` | `explain|what did you mean|point 2|first point|why did you say|elaborate|more detail|can you go deeper` + references to prior text | understander → intent |
| `CORRECTION` | `that's not what i meant|you misunderstood|you're missing|i don't agree with|actually,|no, that's|you assumed` | understander → intent |
| `NEW_INFORMATION` | contains numerals/$/users/customers/new facts; is not an explanation/correction phrasing | understander → intent |
| `CHALLENGE` | `challenge|attack|disprove|stress-test|try to break|prove it wrong` | — |
| `NEW_QUESTION` | question punctuation + new topic (no pronouns pointing at thread) | understander → intent |

LLM fallback reuses the understander call with thread context. If the classifier itself fails → default `NEW_INFORMATION` (re-deliberate; safer than ignoring the user).

### 8.2 Path A — direct answer (EXPLANATION_REQUEST)
One small call (`stage: "direct_answer"`, cap ~500 tokens): given the previous verdict + the specific request, answer plainly with reference to the existing analysis (quote the relevant keyReason/analysis). Zod `{ answer: string }`. No Council run. No new verdict. Turn appended as `direct_reply`. Failure → polite fallback pointing at the verdict sections already on screen.

### 8.3 Path B — targeted re-analysis (CORRECTION / NEW_INFORMATION)
New orchestrator option:

```ts
interface CouncilReconsiderOptions {
  threadContext: ConversationThread;       // original Q, merged context, prior verdict
  reply: string;
  classification: QuestionClassification;
  affectedAgents?: AgentKey[];             // computed, see below
}
```

- **Affected-agent selection (deterministic):** map the new info's gap/fact domain to agent lenses — e.g. budget/cost → `practicalist` (+`skeptic` if risk-adjacent); market/users → `skeptic` + `perspective`; math/code correction → `reasoner`; scope/reframe → `perspective`. Untouched analyses are reused verbatim (they carry `outcome: "COMPLETED"`).
- **Lighter pipeline always** (user decision #8): re-run only affected agents concurrently → comparison (if ≥2 fresh analyses) → Judge. **No Devil's Advocate / Reassessment in follow-ups**, regardless of original mode.
- **Context injection:** agents receive `original question + mergedContext (all prior clarifications/corrections/new info) + note that they are re-evaluating in light of new information + the previous verdict's keyReasons` (so they respond to it without anchor-copying it).
- **Judge:** receives prior verdict + new analyses + untouched analyses + comparison. Prompt addition: *"You are re-deliberating. You may uphold, revise, or overturn the previous verdict. Never defend it for consistency's sake; never overturn it for novelty's sake."* Output must explicitly state `verdictChanged` intent via the normal structured fields.
- **Diff** (§5 `VerdictDiff`) computed deterministically server-side from old vs new verdict and returned with the verdict event.
- On Judge failure → existing deterministic synthesizer path (provisional, degraded) — with the same lighter contract.
- If ALL targeted agents fail → session `failed` with preserved prior thread (existing reliability rules).

### 8.4 Path C — NEW_QUESTION
Starts a fresh thread (new conversation id). Prior thread remains stored.

### 8.5 Path D — CHALLENGE
v0.3 wires the intent only: turns are recorded as challenge intents and the existing `ChallengeButton` (future-marked) gains a working-but-honest state — "Challenge arrives in a later version" — **no fake challenge loop** (unchanged from V0.2.2.1 rule).

## 9. Per-type verdict sets (user decision #7)

Replace the binary PRODUCT / GENERAL split with a type-aware map (proposal — refine during implementation):

| Question types | Verdict set |
|---|---|
| business, decision, planning, comparison, creative | `BUILD` · `BUILD_MVP` · `PIVOT` · `DO_NOT_BUILD` (existing product set) |
| mathematical | `CORRECT` · `INCORRECT` · `PARTIALLY_CORRECT` · `UNVERIFIABLE` |
| explanation, educational | `CONFIRMED` · `REFUTED` · `PARTIALLY_SUPPORTED` · `UNRESOLVED` |
| argumentative | `SUPPORTED` · `UNSUPPORTED` · `MIXED` · `UNDETERMINED` |
| technical | `SOUND` · `FLAWED` · `RISKY` · `UNVERIFIED` |
| troubleshooting | `FIXED` · `DIRECTION_FOUND` · `PARTIAL` · `STILL_UNRESOLVED` |
| general | `AGREE` · `REFINE` · `VALIDATE` · `RECONSIDER` · `REJECT` (kept) |

Mechanics reused from V0.2.2.2: `verdictsForType(type)` drives the Judge prompt contract and the orchestrator's set-enforcement; the synthesizer's degraded mapping gains a per-set fallback (each set gets an explicit "mixed/uncertain" default, never a dead-end). `INSUFFICIENT_INFORMATION` stays system-reserved. `informationSufficiency`, `confidence`, `criticalUnknowns`, `whatWouldChangeVerdict` are unchanged and reported for every verdict, including per-type sets. **This is the largest schema ripple in the version — every consumer of `VERDICT_META`/icons/descriptions (`VerdictView`, `icons.tsx`, tests) must be extended; `verdictSchema`'s enum accepts the full union.**

## 10. API contract changes

| Endpoint | Purpose | Notes |
|---|---|---|
| `POST /api/council` (existing) | Initial convene | Body extended with optional `context.clarifications?: {question, answer}[]`. Events unchanged + verdict events may carry `diff` when `reconsider` used. |
| `POST /api/council/clarify` (new) | Understanding gate result | → `{ questions?, restatedQuestion?, assumptions?, critical }`. No model call when the bank/gate answers deterministically. |
| `POST /api/council/followup` (new) | Reply after a verdict | Body: `{ thread: ConversationThread (summarized), reply, mode }` → SSE: `followup:intent` event first, then either `direct:reply` or normal deliberation events ending in `verdict` (+`diff`). |
| `POST /api/council/direct` (new, optional) | Explanation-only call | Used by followup when intent = EXPLANATION_REQUEST. Could be folded into followup. |

All endpoints stay stateless (context travels in the body), SSE-streamed, Zod-validated, same reliability guarantees (abort, timeout, cancel, retry, partial preservation).

## 11. Client changes (minimal, no redesign)

- `lib/client/conversationState.ts` (new): pure reducer over `ConversationThread`; composes per-turn council phases (a turn can be in `analyzing → complete/degraded/failed/cancelled`); guards duplicate submissions per turn.

- `lib/client/persistence.ts`: new key `council.threads.v1` storing **summarized turns** (per user decision #10: question + reply + final verdict + diff; no raw per-turn analyses). Old `council.sessions.v1` untouched. Same caps (e.g. max 5 threads, 500KB, versioned, quota-safe).
- Components (functional wiring only, existing visual language):
  - `CouncilApp.tsx`: render a compact input under the verdict card ("Continue the conversation…") + the turn thread above it; wire `sendFollowUp` / `answerClarification`; disable input while a turn is active; show clarification questions inline as a card with an input each.
  - `VerdictView.tsx`: when `diff` present, render a small "changed vs previous" strip (category/score/confidence deltas + reasons added/removed).
  - `QuestionScreen.tsx`: unchanged except context-plug (prefill a new question starts a fresh thread).
  - `ChallengeButton.tsx`: intent wiring only (§8.5) — still honestly future-marked.
- The soft turn-limit note (§5) renders as a small inline hint.

## 12. Performance & cost guardrails

- The understander/clarify call only fires when the heuristic gate says *critical* (or cloud is available) → most questions cost **zero extra calls**.
- Direct answers = 1 small call; targeted re-analysis = 1–2 affected agents + comparison + Judge (bounded, no DA/reassessment); auto-degraded regardless of original mode.
- Reuse existing per-stage output caps + telemetry (`usage.calls`); add new stages `understanding`, `direct_answer` to `CouncilCallTelemetry.stage` + `stageDurations` (client-facing rows tolerate unknown keys).
- Independent agents stay concurrent (`Promise.all`), untouched analyses are never re-called.
- **Measured target:** a typical follow-up reply (targeted path) should cost ≤ 2–4 model calls and finish in the low minutes, vs an 8–17 min full re-run today.

---

## 13. Reliability & error handling (carried forward, extended)

- Understander / classifier / direct-answer failures → graceful degradation: proceed with heuristics; never block; never expose raw errors (map to the existing friendly messages: provider unreachable, timed out, interrupted, invalid).
- Re-deliberation partial failure → preserve prior thread + completed new analyses; `failed`/`degraded` per existing phase rules.
- Cancellation mid-clarification → thread stays; user can re-answer.
- No new server state; abort-safe SSE; listener cleanup on unmount; no memory leaks.

## 14. Testing plan

7. Per-type verdict sets: Judge contract per type; set-enforcement; synthesizer per-set defaults; never dead-end; INSUFFICIENT_INFORMATION never offered.
8. Persistence: summarized-turn round-trip; refresh restores thread; version bump tolerance.
9. Reliability regressions: agent fail / Judge fail / malformed / timeout / cancel / duplicate-submit / partial results — all still green; no refresh required after failure.

**Manual end-to-end (existing 9 scenarios from the brief):**
- A expert prompt, B normal, C layman ("should i start a clothing business"), D informal ("should i leave uni and just build apps?"), E ambiguous ("should i build this app?"), F follow-up correction ("you misunderstood"), G new critical fact after verdict ("i already have 5,000 users"), H disagreement, I explicit challenge intent.
